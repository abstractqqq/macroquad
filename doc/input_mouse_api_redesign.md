# Input and Mouse API Redesign Plan

## Goal

Replace the keyboard and mouse `HashSet` state in the main `macroquad` crate
with compact, deterministic structures that:

- make the common `is_*` queries allocation-free and cheaper than hashing;
- preserve the order of key transitions within a frame;
- make `get_last_key_pressed` return the actual last key pressed;
- avoid allocating unless the caller requests a collection of all keys;
- keep frame, window-focus, and touch-to-mouse behavior unchanged.

This is a private fork, so compatibility with the current collection return
types is not required.

## Current State

`Context` owns six standard-library hash sets:

- `keys_down`
- `keys_pressed`
- `keys_released`
- `mouse_down`
- `mouse_pressed`
- `mouse_released`

The boolean APIs query these sets directly. The three `get_keys_*` functions
clone entire sets, and `get_last_key_pressed` returns an arbitrary set element.
Frame cleanup clears transition sets, while window minimization drains the
held sets into the released sets.

## Proposed Representation

### Keyboard

Introduce an internal keyboard state:

```rust
struct KeyboardState {
    down: KeyBits,
    pressed: KeyBits,
    released: KeyBits,
    down_order: Vec<KeyCode>,
    pressed_order: Vec<KeyCode>,
    released_order: Vec<KeyCode>,
    last_pressed: Option<KeyCode>,
}
```

`KeyBits` should be a fixed-size bitset backed by `[u64; N]`. Add an explicit
internal conversion between `KeyCode` and a dense index:

```rust
fn key_index(key: KeyCode) -> Option<usize>;
fn key_from_index(index: usize) -> Option<KeyCode>;
```

Do not cast `KeyCode` to an integer or depend on miniquad's enum
discriminants. An explicit mapping makes unsupported or newly added variants
visible during maintenance.

Responsibilities of each field:

- `down` provides constant-time held-key queries.
- `pressed` and `released` provide constant-time transition queries.
- `pressed_order` and `released_order` preserve event order.
- `down_order` allows `keys_down()` to return deterministic press order
  without scanning every possible key.
- `last_pressed` records the most recent non-repeat press even when the same
  key is pressed more than once in a frame.

The vectors contain no duplicates. The transition bitsets are used to enforce
that invariant.

### Mouse

Introduce a separate mouse button state:

```rust
struct MouseButtonState {
    down: u16,
    pressed: u16,
    released: u16,
}
```

Use an explicit `MouseButton` to bit conversion. Reserve a bit for every
supported button, including `Unknown` only if existing behavior requires it.
Mouse button ordering can be canonical because there is currently no public
API that reports the last mouse button transition. If ordered mouse transition
APIs are added later, add small ordered vectors using the same approach as the
keyboard.

Keep mouse position, local position, delta, wheel, cursor grab, and touch
simulation fields outside this structure.

## Event Semantics

### Key down

For a non-repeat key-down event:

1. If the key is not already in `down`, set it and append it to `down_order`.
2. If the key is not already in `pressed`, set it and append it to
   `pressed_order`.
3. Keep forwarding the original event to coroutine input subscribers.
4. Preserve the existing `UpdateTrigger` scheduling behavior.

Repeat events must not add duplicate pressed transitions. Preserve the current
rule that `repeat == true` does not mark a key as newly pressed.

### Key up

1. Clear the key from `down`.
2. Remove it from `down_order`.
3. If it is not already in `released`, set it and append it to
   `released_order`.
4. Continue forwarding the original event.

`down_order` is expected to remain very small, so a linear removal is
appropriate. If profiling disproves this, store positions alongside the
bitset.

### Mouse down and up

Set or clear the relevant bits while retaining the current behavior for:

- simulated left-button events generated by touch;
- cursor position updates;
- mouse enter and leave;
- update scheduling;
- coroutine event forwarding.

### End of frame

Clear:

- keyboard `pressed`, `released`, `pressed_order`, and `released_order`;
- mouse `pressed` and `released`;
- mouse wheel delta.

Retain keyboard and mouse `down` state across frames.

### Window minimization and mouse leave

Window minimization must convert every held key and mouse button into a
released transition before clearing held state. Append keyboard releases in
`down_order`, which gives deterministic behavior.

Mouse leave must preserve the current held-button release behavior. Verify
whether all platforms send a corresponding enter event before changing any
semantics in this area.

## Public API

Keep the common boolean queries:

```rust
pub fn is_key_pressed(key: KeyCode) -> bool;
pub fn is_key_down(key: KeyCode) -> bool;
pub fn is_key_released(key: KeyCode) -> bool;

pub fn is_mouse_button_pressed(button: MouseButton) -> bool;
pub fn is_mouse_button_down(button: MouseButton) -> bool;
pub fn is_mouse_button_released(button: MouseButton) -> bool;
```

Change the aggregate keyboard APIs to ordered vectors:

```rust
pub fn keys_pressed() -> Vec<KeyCode>;
pub fn keys_down() -> Vec<KeyCode>;
pub fn keys_released() -> Vec<KeyCode>;
pub fn last_key_pressed() -> Option<KeyCode>;
```

`last_key_pressed()` returns the separately tracked `last_pressed` value.

Remove the existing `get_keys_pressed`, `get_keys_down`,
`get_keys_released`, and `get_last_key_pressed` functions rather than keeping
compatibility wrappers.

Do not expose borrowed slices from the global context. The current global
mutable-context architecture cannot provide a clean frame-scoped lifetime,
and returning owned, normally tiny vectors keeps the API straightforward.

Consider grouping mouse queries under a snapshot-style API only as a separate
follow-up. It is not necessary to realize the data-structure and correctness
benefits in this change.

## Implementation Sequence

1. Inventory all `KeyCode` and `MouseButton` variants in the pinned miniquad
   version.
2. Add dense conversion functions and unit tests proving round trips for every
   supported variant.
3. Implement and unit-test `KeyBits`.
4. Implement `KeyboardState` transition and frame-reset methods.
5. Implement `MouseButtonState` transition and frame-reset methods.
6. Replace the six `HashSet` fields in `Context`.
7. Route key, mouse, touch-simulation, mouse-leave, and window-minimize events
   through the new state methods.
8. Replace the public aggregate functions with the ordered `Vec` API.
9. Update examples, tests, and internal call sites that use the removed names
   or expect `HashSet`.
10. Run correctness tests and targeted benchmarks.

Keep each event handler responsible for event forwarding and scheduling.
State mutation should be centralized in the new state types so that edge-case
behavior can be tested without constructing the rendering context.

## Tests

Add unit tests for:

- every supported key and mouse button maps uniquely;
- key and button mappings round-trip;
- key down sets both held and pressed state;
- repeated key-down events do not duplicate `pressed_order`;
- a repeat event does not create a new pressed transition;
- key up clears held state and records one release;
- press and release within one frame reports both transitions;
- multiple transitions preserve their event order;
- `last_key_pressed` returns the final transition;
- frame reset clears transitions but retains held state;
- window minimization releases every held key in deterministic order;
- mouse leave releases held mouse buttons;
- touch simulation still drives the left mouse button;
- `clear_input_queue` clears the same state it clears today.

Run the existing main-crate test suite with default and all features.

## Benchmarks

Create a small release-mode benchmark covering:

- repeated `is_key_down` and `is_key_pressed` queries;
- key-down and key-up transitions;
- end-of-frame clearing;
- collecting all down and pressed keys;
- mouse button queries and transitions.

Compare the current `HashSet` implementation against the proposed structures
using realistic set sizes: zero, one, four, and twelve held keys. Report
latency per operation and allocation counts for aggregate getters.

Performance acceptance criteria:

- boolean queries and transitions must not regress;
- common boolean queries must allocate zero times;
- frame reset must allocate zero times after initial vector capacity growth;
- aggregate getters may allocate exactly once for a non-empty result;
- no benchmark result should justify sacrificing event-order correctness.

## Risks and Mitigations

- **Incomplete key mapping:** exhaustive mapping tests and a clearly handled
  unsupported-key path prevent silent aliasing.
- **Minimization or focus semantic changes:** encode current drain-to-release
  behavior in tests before replacing it.
- **Duplicate transitions:** centralize mutation and use transition bitsets as
  deduplication guards.
- **Vector capacity churn:** retain vector capacity across frame resets and
  initialize with a modest capacity.
- **Future miniquad variants:** keep conversions in one module and make the
  variant inventory part of miniquad upgrade work.

## Non-Goals

- Redesigning touch storage.
- Redesigning coroutine input event delivery.
- Changing blocking event-loop scheduling.
- Adding gamepad support.
- Providing compatibility with the removed `HashSet` APIs.
- Refactoring the global `Context` ownership model.

## Definition of Done

The redesign is complete when:

- the main crate contains no keyboard or mouse `HashSet` state;
- all boolean and aggregate input APIs use the new representation;
- key transition order is deterministic;
- `last_key_pressed` is correct;
- existing touch, focus, and event-loop semantics are covered by tests;
- default and all-feature main-crate tests pass;
- benchmark results and the final representation are documented.
